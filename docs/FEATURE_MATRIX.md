# Open stack vs vendor stack: feature matrix

As of: 2026-10-03 16:15 (local time). Camera mapping: cam-A = T31, cam-B = T23, cam-C = T20, cam-D = T21, cam-E = T10, cam-F = T41.

See also: [OPENIMP_BEYOND_VENDOR.md](OPENIMP_BEYOND_VENDOR.md) (integration notes for streamer authors on everything marked beyond vendor).

Open stack = open-tx-isp (kernel driver) + OpenIMP (libimp) + timps. Vendor = tx-isp-*.ko + Ingenic libimp.

## Summary

**What is complete**

- All five original test cameras (cam-A T31, cam-B T23, cam-C T20, cam-D T21, cam-E T10) run fully on the open kernel driver, OpenIMP and timps from flashed images; cam-F (T41) boots our driver and OpenIMP from flash (-all-13); no Ingenic/neo helper libraries any more, and on T23 no helixd and no vendor libimp either.
- Core functions are backed by evidence: H.264 on all six SoCs (soaks up to 2 h 53 without errors), HEVC on T31, hardware JPEG/MJPEG, second stream, OSD (text, bitmap, rectangle, line), real motion detection, day/night, flip.
- Beyond the vendor: reload/stop robustness (0 oops in 10 cycles each), smaller libimp (~0.5–0.6 MB instead of 1.0–1.3 MB), more free video memory on T21 (2.76 MB instead of ~1.2 MB), T31 module smaller than vendor, T21 controls and noise reduction take effect (the vendor ignores them), T31 AEC with −18 dB echo, reference-frame sharing on T21/T23 (~1.5 MB less video memory, on by default).

**Biggest gaps**

- T23 daylight: the green-yellow cast is fixed on claude/t23-day-color (bc70f10b, device-tested in sunlight, neutral colours) and is no longer a gap once flashed (-all-13). Cause: the WB gains were reset to 1x on every stream start (each on-demand snapshot restarts the stream); the vendor keeps the AWB state. The same reset also showed the cast briefly at every preview start without a viewer (stream restart reset WB to 1x). The HLIL substitute AE fast start (~4 s instead of ~2 min) is in the same branch. Remaining: backlight/highlight only with vendor AE, real WDR missing (port of the dynamic ADR).
- T23 stability: three unexplained hard hangs in sun and one reboot with several parallel streams (memory pressure?) – not reproduced; the conspicuously large JPEGs (~730 KB at q75) are also unexplained.
- T41 (cam-F): flashed with an open-stack kernel + rootfs and streaming with the fully open stack (open driver + OpenIMP + timps) after the gc5603 tuning-file fix (claude/t41-gc5603-fix); untested on T41: day/night, AE/AWB quality, audio; short ~1.2-s IVS gaps are still being looked at. T10 (cam-E): only bring-up level documented; day/night after the drift fix and AE/AWB/image controls not documented.
- T20/T21 white balance and controls: T20 uses the OpenIMP "simple AWB" as default (vendor chain behind a switch, daylight test open); table Sinter has no effect on T20, as in the vendor; RC modes Capped*/SMART are still mapped to VBR on T10/T20/T21, where QP steps, staticTime/changePos/qualityLvl, I/P delta and bias are accepted but ignored (vendor eprc controller port in progress); T31 plain VBR and CappedVBR are closed loop now; RC readback on T20/T21 returns the vendor-clamped values.
- Feature gaps per SoC: H.265 only on T31 (T21/T23 planned, lowest priority), AEC documented only on T31 (T23 implemented, device test open), reference sharing now works on T21/T23 (on by default, saves ~1.5 MB), T21 kernel module 805 KB instead of 616 KB.
- Known gaps from the 2026-10-03 device tests (all in work): T41 rate control ignores the bitrate setting (about 8.2 Mbit/s), T41 WB POST gave a black picture, T41 flip has no effect, one spontaneous T41 reboot (not reproduced); T23 brightness/contrast/saturation/hue have no visible effect and T23 sub-stream rotation fails; T10/T20 ae_it_max_us has no effect; T10 kernel WARN "Data will not fit into plane" in the FS tick (no oops).

Current state: cam-A, cam-C, cam-D, cam-E on open-tx-isp-all-11 / openimp-all-10 (kernel with soc_vpu patch 0099); cam-B on -all-12 / openimp-all-10 (HLIL AE default, vendor AE optional); cam-F (T41) on -all-13 (our driver and OpenIMP boot from flash). The next aggregate -all-13 is being built: reference ring on T21/T23, T31 privacy mask, T21 controls, encoder error limit, rate-control changes, T23 day-colour fix, AVPU fixes, kernel patch 0100 and timps fixes (3da95b6); it is not flashed yet.

Marked [-all-13] = tested but not flashed yet: T31 privacy mask, T21 controls + sinter_strength, T21 debug parameters removed, reference ring on T21/T23 (claude/t23-ref-ring), RC modes (claude/rc-modes-2), T20/T21 encoder error limit, T23 RC app-0 defaults, T20/T21 RC readback, sc4336p vflip fix, timps T23 AU limit 2 MiB+64 KiB (a0fdde8), T23 day-colour fix (bc70f10b, 390bc47c, HLIL fast start), AVPU review fixes, kernel patch 0100, timps 3da95b6 (OSD clock redrawn on idle to active; the first snapshot after idle showed a stale clock, tested on another T31).

In progress: vendor-identical eprc port on T21 (T23 eprc: claude/eprc-t21-t23, not yet in an aggregate), full port of the vendor RC core on T31 (CappedQuality), device test of the OSD thick lines (claude/osd-thick-lines), T41 rate control, WB and flip, T41 short IVS gaps; untested on T41: day/night, AE/AWB quality, audio. Built, device test pending: OPENIMP_T10_RC_SUPERFRM, OPENIMP_EPRC_QP_DOWN1/2. Not adopted: OSD edge flush, reference sharing on T10/T20/T31 (hardware missing).

## Legend

- ✅ supported: works, matches vendor behaviour, tested or backed by the changelog
- ✅+ improved beyond vendor: more robust, leaner or more functional than the vendor stack
- ⚠️ known defect / deviation: runs, but with a known defect or a deviation from the vendor
- 🔧 in progress: branch is running or a test is pending
- 📋 planned: deliberately scheduled, not started yet (mostly low priority)
- ❌ missing: not implemented
- — hardware does not have it: not applicable
- ? unknown: not documented in the sources, deliberately not guessed
- [-all-13]: tested but not flashed yet

- **White balance (AWB, presets, manual)**: T20: awb_normalise bug and swapped preset direction fixed (Wyze: preset 4 very blue, 7 warm), CPU of the vendor chain +4 %, JPEG +40 % larger. Hysteresis/freeze [-all-11 flashed], restore fix from review. timps (simulation-tested, device test open): WB modes 0..9, custom WB hidden on T10/T20/T30. T23: the colour cast with a white LED was only configuration (manual WB in timps.conf). T23 daylight: the green-yellow cast is FIXED on claude/t23-day-color (bc70f10b) [-all-13]. Cause: our driver reset the WB gains to 1x on every stream start, and every on-demand snapshot restarts the stream, so snapshots were taken before AWB had re-converged; the vendor keeps the AWB state across stream restarts. Commit 390bc47c additionally writes the vendor values for top 0x1c and GIB 0x1008/0x1010 at stream start. Device-tested on cam-B in sunlight: neutral colours, gains kept (0x710/0x7c0). Not flashed yet. T41 (cam-F), 2026-10-03: the black picture after the WB POST is not fully isolated (the test's own base reset also posted WB gains 0); a controlled retest is in work. T31: the test ran in night/mono mode, no colour, WB still open.

### Video encoder and streams

- **H.264**: T23: bitstream overflow (frame >1 MiB) fixed, window 2 MiB; the hardware ignores the window and overwrote the reference buffer – a hang candidate. timps AU limit for T23 set to 2 MiB+64 KiB (a0fdde8) [-all-13/timps]. timps OSD clock: the first snapshot after idle showed a stale clock (minutes to hours); fixed in timps 3da95b6 (text redrawn on idle to active), tested on another T31, ships with the next images. T10: NVPU writes 21/10 KB behind each reference plane, references enlarged accordingly. T20/T21: error limit (3 bad frames → encoder restart, 2 re-creations → channel stops) instead of 20 s per frame [-all-13]. IDR at FIXQP = QP−3 as vendor. 
- **H.265 / HEVC**: Before: H.265 accepted, stream empty. T31: own lambda tables by formula (bit-identical, 12 documented ±1).
- **JPEG / MJPEG / snapshot**: Helix HW JPEG: ~95 % less CPU per snapshot. Quality is applied (before: fixed 75); on truncation quality −5 as vendor, +5 after 100 clean frames (beyond vendor). When VPU/rmem is tight: the last JPEG is reused instead of blocking. T21: the hardware ignores the JPEG size limit, the core loses the last 128-byte burst per job (as vendor, compensated). The dedicated JPEG channel never received frames → timps restarted the frame source (fixed on all SoCs).
- **Sub-stream / scaler (ch1 640×360)**: T10: `_update_ds()` divided the output width by the output width (ratio always 1.0); applies to the shared T20/T10 firmware code.
- **Rate-control mode (CBR/VBR/FixQP/Capped*/SMART)**: Before: silently CBR. Reconstructing the vendor registers (RC_VIDEO_CFG/FRAME_START/END) is an open improvement proposal (large). T31: CappedVBR/CappedQuality closed-loop with PSNR cap 42 dB (claude/rc-modes), plain VBR closed loop by default (cam-A measurement above). T10/T20/T21: mode, bitrate, QP range, GOP and fps take effect; QP steps, staticTime/changePos/qualityLvl, I/P delta and bias are accepted but ignored. A port of the vendor eprc controller is in progress (claude/t23-smart); T21 uses the same controller as T23, T20/T10 a different, smaller one. All in claude/rc-modes-2 -> -all-13. One log line per channel with the effective RC; invalid QP/fps are clamped with a warning (beyond vendor). Device tests 2026-10-03 (60 s, target 1200 kbit/s, decode clean): T23 eprc SMART 1141, CBR 1253, VBR 1255 (branch claude/eprc-t21-t23, not yet in an aggregate). T21 eprc approximation (OPENIMP_T21_EPRC=1): CBR 1338, VBR 1237, SMART 1356 against 570 for the old controller; a vendor-identical T21 port is in work. T20 OEM controller (OPENIMP_T20_RC=1, opt-in; kernel patch 0101 lets it read the NVPU statistics registers): CBR 1435 (+19 %; the offline study shows the vendor controller overshoots as well), VBR 1329, SMART 983; the old controller gave CBR 942. T10 CBR at 2500 gave 3872 kbit/s (+55 %), 400 gave 352. T41 (cam-F): the encoder delivers about 8.2 Mbit/s regardless of the bitrate setting (in work). Opt-in improvements beyond the vendor, built but not device-tested yet: OPENIMP_T10_RC_SUPERFRM=1 (T10 VBR super-frame fix), OPENIMP_EPRC_QP_DOWN1=1/2 (eprc QP-down limit); see OPENIMP_BEYOND_VENDOR.md.
- **RC parameters (QP steps, staticTime, changePos, qualityLvl, I bias)**: T23: the qualityLvl/changePos mapping is partly derived from SDK text, not from vendor code. A one-off "helix vpu error interrupt status=100" after the change, unexplained. timps VBR changes as a result (target 80 %, P-QP step max 3). Correction: the vendor-clamped values returned on T20/T21 when the app passes 0 are staticTime 1, changePos 50, qualityLvl 0, QP steps 2/2 (earlier assumption 1/80/2 was wrong).

### Memory, size, load

- **libimp size (code + data)**: Figures from the changelog section "Compared with the vendor stack".
- **Kernel module size**: T21: static data from the lifted AE/ADR/AWB code; still open (functions duplicated as C reimplementation and lift, ~7–9 KB). T23 module RAM is intentionally larger because of reconstruction.
- **Video memory (rmem) / MemFree**: T21: the MemFree reserve with main+sub was originally only 0.5 MB → WebRTC switching failed; fixed. T10 (device test 2026-10-03): MemFree 1.9–2.8 MB of 37.7 MB.
- **Reference-frame sharing (BUF_SHARE_CFG)**: Only T21/T23 (Helix) have ring mode; T10/T20/T31 hardware has none (user decision: not pursued there). The vendor T23 stack uses the reference ring by default (measured on cam-B: register 0x60004 bit 30 set, luma ring 1920x(1088+256), chroma 1920x(544+128)); the vendor libimp forces it on in CreateChn for channels up to 1920x1088. Root cause of the earlier artefacts: the per-frame wrap byte was not copied into the motion-estimation control word (0x50000 bits 14..21). Found by dumping the vendor's encoder command lists with an LD_PRELOAD shim. User decision: on by default on T21/T23 (<=1920x1088), OPENIMP_REF_SHARE=0 disables; goes into -all-13.
- **CPU load (documented figures)**: HW JPEG saves ~95 % CPU per snapshot; IVS optimisation T20 4.1→2.7 %; T21: 346 runtime address translations in the lift pending. No systematic vendor-versus-open CPU comparison in the sources.
